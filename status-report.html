1 · Executive Summary

OptiFeed is a monorepo web application for automating pond feeding on shrimp/fish farms. An ESP32 energy controller dispenses feed and reports telemetry (hopper level, water temperature, feed events) via authenticated device endpoints; a farmer-facing dashboard (English + Hiligaynon) drives schedule, settings, biomass logging, feeding history, growth/FCR charts, notifications, and an AI chat assistant.

All 10 remediation work packages (WP-0 … WP-9) are now implemented and verified on the local Karl branch, including the final one (WP-2 — schedule/settings persistence) completed this session. The app builds clean: lint, typecheck, and production build all pass.

Status: FUNCTIONAL. Real Supabase authentication is wired (one login per pond, Farm ID + PIN), every dashboard read is scoped to the signed-in owner, and the previously-broken pause toggle, stale hopper reads, dual-source-of-truth settings, and wrong-table feeding history are all corrected.

Request pipeline

proxy.ts (Next 16 middleware) runs next-intl/middleware once, then refreshes the Supabase session and gates navigation: unauthenticated /dashboard* → login, authenticated /login → dashboard. Redirects apply to GET/HEAD only, so Server Action POSTs reach their route handler and keep their RSC / x-action-redirect response (fixes the "An unexpected response was received from the server." failure). Locale rewriting, cookie refresh, and auth cookies all mutate the single intl response.

5 · Auth & Security

Farm ID + PIN
Backing auth
Supabase
Device auth
x-device-token
Session scoping
ownerId
  • One login per pond. Farm ID maps to a synthetic email (farmId@pond.optifeed.local); the static 4–6 digit PIN is the Supabase password. No shared hardcoded PIN — loginWithPin() calls signInWithPassword().
  • Owner-scoped reads/writes. getCurrentPondOwnerId() derives the owner from the Supabase session; every Server Component/action replaces the former literal "demo-farmer-1". saveBiomassLog() validates the submitted pond belongs to the owner (cross-tenant guard).
  • Proxy gate. Dashboard routes redirect unauthenticated visitors to /login; sign-out clears the session and returns to login.
  • Device side is independently secured — /api/ingest requires a per-device token checked against the DB.
  • Demo fixture. scripts/provision-demo-user.ts (idempotent, service role) provisions the demo user. Login: Farm ID demo-farmer-1 / PIN 1234 (user 4e838850-1e93-442e-9168-0e59145a044e). PIN hint removed from UI copy.
