Critical Findings

#1 — Production Secrets Committed to Git
Critical
File
apps/web/.env
Category
Secrets Management

The .env file contains live production credentials committed to the repository:

  • DATABASE_URL — Full PostgreSQL connection string with plaintext password
  • DIRECT_URL — Same password in a second connection string
  • NEXT_PUBLIC_SUPABASE_ANON_KEY — Supabase JWT
  • SUPABASE_SERVICE_ROLE_KEY — Full admin access bypassing all RLS
  • GEMINI_API_KEY — Google Gemini API key in plaintext
apps/web/.env
# All of these are REAL production credentials
DATABASE_URL="postgresql://...:sU2YVmhZVwv%26J%24b@..."
DIRECT_URL="postgresql://...:sU2YVmhZVwv%26J%24b@..."
NEXT_PUBLIC_SUPABASE_URL="https://xjjnkikgkraixlfhhvoh..."
NEXT_PUBLIC_SUPABASE_ANON_KEY="eyJ..."
SUPABASE_SERVICE_ROLE_KEY="eyJ..."
GEMINI_API_KEY="AQ.Ab8RN6KZy..."

Although .gitignore lists .env, the file is already tracked by git. Anyone with repository access has unrestricted database admin control.

Action: Rotate ALL credentials. Run git rm --cached apps/web/.env. Add a pre-commit hook to prevent re-commit.

#2 — Hardcoded Device Token in Firmware
Critical
Files
firmware/firmware-main.ino:42
prisma/seed.ts:49
Category
Credential Exposure

The device authentication token is hardcoded in both firmware and seed data:

firmware/firmware-main.ino:42
#define DEVICE_TOKEN    "esp32-tok-cict-001"
#define DEVICE_MAC      "A4:CF:12:7E:3B:09"
prisma/seed.ts:49
token: "esp32-tok-cict-001",

Token compromise allows impersonation of the device to inject fake telemetry, trigger unauthorized feed dispenses, or manipulate schedules.

Action: Use environment variables or per-device provisioning. Never hardcode tokens in firmware source.

#3 — Brute-Forceable PIN Auth with No Lockout
Critical
Files
lib/actions/auth.ts:10-28
proxy.ts:67
Category
Authentication

Authentication uses a 4-6 digit numeric PIN (10,000 to 1,000,000 combinations) with:

  • No rate limiting on login attempts
  • No account lockout after failed attempts
  • No CAPTCHA or bot protection
  • No progressive delay on repeated failures
lib/actions/auth.ts:10-12
if (pin.length < 4 || pin.length > 6)
  return { error: "invalid" };
// No rate limiting, no lockout, no CAPTCHA

Additionally, the login form pre-fills demo-farmer-1 with default PIN 1234.

Action: Implement rate limiting (e.g., 5 attempts per minute), account lockout after 10 failures, and progressive delays.

High Findings

#4 — No Rate Limiting on Login or API Endpoints
High
Files
api/chat/route.ts
api/import/route.ts
api/export/route.ts
Category
Abuse Prevention

The only rate limit in the entire codebase is a per-device 1-second throttle on /api/ingest. All human-facing endpoints are unprotected:

  • Login — brute-forceable (see #3)
  • Chat API — can drain Gemini API quota
  • Export endpoints — data exfiltration at scale
  • Import endpoints — database flooding

Action: Add global rate limiting middleware (e.g., express-rate-limit pattern) for all API routes.

#5 — API Routes Excluded from Middleware Auth
High
File
proxy.ts:67
Category
Authorization
proxy.ts:67
matcher: ["/((?!api|_next|_vercel|.*\\..*).*)"],

All /api/* routes are excluded from the Next.js middleware that performs Supabase session refresh and auth redirects. While some API routes check auth independently, this creates a fragile pattern where any new API route added without explicit auth check is unprotected.

Action: Create a shared requireAuth() helper and apply it to all dashboard API routes.

#6 — Missing Ownership Validation in Server Actions
High
Files
lib/actions/settings.ts:8-66
lib/actions/time.ts:7-38
lib/actions/energy.ts:113-140
lib/actions/notifications.ts:100-115
Category
Authorization

Multiple server actions accept pondId or deviceId without verifying the authenticated user owns the resource:

  • updatePondSettings — ownership check missing in fallback path
  • setDeviceTime — device ownership not verified against caller's pond
  • registerEnergyDevice — no ownership verification at all
  • createDemoNotification — zero auth check; any user can create notifications for any pond

Action: Add ownership verification at the top of every server action that accepts resource IDs.

#7 — No Security Headers Configured
High
File
next.config.ts:1-14
Category
Security Headers
next.config.ts
const nextConfig: NextConfig = {
    serverExternalPackages: ["@prisma/client"],
    allowedDevOrigins: ["192.168.1.10"],
    devIndicators: false,
    // No security headers at all
};

Missing headers: Content-Security-Policy (XSS protection), X-Frame-Options (clickjacking), Strict-Transport-Security (HTTPS enforcement), X-Content-Type-Options (MIME sniffing), Referrer-Policy, Permissions-Policy.

Action: Add a headers() config to next.config.ts with all standard security headers.

#8 — No CORS Configuration
High
Scope
All API routes
Category
Cross-Origin Security

No CORS headers or middleware found anywhere in the codebase. For an IoT application where ESP32 devices make cross-origin HTTP requests, CORS behavior is undefined. Cross-origin requests are governed only by browser same-origin policy and Next.js defaults.

Action: Configure explicit CORS headers for device API routes (/api/ingest, /api/feed-command, /api/schedule-sync) and restrict dashboard API routes to same-origin.

#9 — No Row-Level Security in Database
High
File
prisma/schema.prisma:5
Category
Data Security
prisma/schema.prisma:5
// TODO(karl): Confirm indexes, cascading deletes,
// and row-level security policies once the access
// model is finalized.

The schema has no RLS policies despite using Supabase PostgreSQL. All access control depends entirely on application-level ownerId lookups, which as documented above are inconsistent. A direct database query bypasses all access controls.

Action: Enable Supabase RLS policies on all tables. Use auth.uid() to enforce row-level access at the database layer.

#10 — Error Details Leaked to Client
High
File
api/import/confirm/route.ts:191
Category
Information Disclosure
api/import/confirm/route.ts:191
return Response.json(
  { error: "Import failed", details: String(error) },
  { status: 500 }
);

Server-side errors (including Prisma query details, stack traces, and internal state) are serialized and returned to the client in the import confirm endpoint. This exposes internal implementation details to attackers.

Action: Return generic error messages to clients. Log full errors server-side only.

#11 — Device API Routes Have Zero Error Handling
High
Files
api/feed-command/route.ts
api/schedule-sync/route.ts
Category
Reliability

The feed-command and schedule-sync endpoints that the ESP32 polls every 5 seconds have no try/catch blocks. If Prisma queries fail, raw 500 errors propagate to the firmware, which could cause firmware hangs or stuck states.

  • /api/feed-command — no error handling at all
  • /api/schedule-sync — no error handling at all
  • /api/export — no error handling
  • /api/export/batch — no error handling

Action: Wrap all device-facing endpoints in try/catch with structured error responses and server-side logging.

#12 — N+1 Query and No Transaction in Import
High
File
api/import/confirm/route.ts:54-170
Category
Performance / Reliability

The import handler inserts rows one at a time in a for-loop with individual prisma.feedEvent.create() calls. For a CSV with hundreds of rows, this creates N database queries. Additionally, no transaction wrapping means a partial import commits without rollback.

api/import/confirm/route.ts (simplified)
// One-by-one inserts in a loop — no batch, no transaction
for (const row of data) {
    await prisma.feedEvent.create({ data: { ... } });
}
// If import fails halfway, partial data is committed

Action: Use prisma.$transaction() with prisma.createMany() for batch inserts.

Medium Findings

#13 — No Test Framework
Medium
Scope
Entire codebase
Category
Quality Assurance

Zero test files exist in the codebase. No Jest, Vitest, Mocha, or Playwright configuration. No *.test.* or *.spec.* files. No test-related devDependencies. Verification relies solely on pnpm lint + pnpm build.

Action: Add Vitest for unit tests and Playwright for E2E. Start with critical paths: auth, feed requests, schedule commands, and import/export.

#14 — No Health Check Endpoints
Medium
Scope
All API routes
Category
Operability

No /health, /healthz, or /readyz endpoints exist. Load balancers, monitoring tools, and orchestrators cannot probe application readiness or liveness.

Action: Add /api/health that checks database connectivity and returns status.

#15 — No Graceful Shutdown Handling
Medium
Scope
Application process
Category
Reliability

No SIGTERM or SIGINT handlers. When the process is killed during deploy or restart, in-flight Prisma transactions will be aborted and in-progress SSE streams (chat) will be terminated abruptly.

Action: Add process signal handlers to drain connections gracefully before shutdown.

#16 — No Structured Logging
Medium
Scope
Entire codebase
Category
Observability

Only console.log / console.error / console.warn with ad-hoc prefixes. No logging library (winston, pino, morgan). No log levels, no correlation IDs, no structured JSON output for log aggregation.

Action: Adopt a structured logger (e.g., pino) with log levels, request IDs, and JSON output.

#17 — Gemini API Key Prefix Logged
Medium
Files
lib/gemini.ts:22-28
api/chat/route.ts:63
Category
Information Disclosure
lib/gemini.ts:22-28
export function geminiDebugInfo() {
    return {
        hasKey: isGeminiEnabled(),
        keyPrefix: apiKey ? apiKey.slice(0, 6) : "none",
        nodeEnv: process.env.NODE_ENV ?? "unknown",
        model: getGeminiModelId(),

The first 6 characters of the Gemini API key are logged on every chat request. This reduces the keyspace for brute-force attacks and may appear in log aggregation services.

Action: Remove key prefix from debug info. Only log hasKey: boolean.

#18 — No Prompt Injection Protection on Chat
Medium
File
api/chat/route.ts:39-49
Category
AI Safety

User messages are passed to Gemini with only a typeof check and a 20-turn history limit. No sanitization or prompt injection protection exists. An attacker could craft messages to manipulate the AI's behavior, extract the system prompt, or bypass safety guardrails.

Action: Add input sanitization, validate message length, and consider content filtering before sending to Gemini.

Multiple magic numbers and utility functions are duplicated across the codebase:

#22 — Unbounded Export Queries
Medium
Files
api/export/route.ts
api/export/batch/route.ts
Category
Performance

Export endpoints fetch all records with no take limit. A table with millions of rows would create a very large CSV or ZIP response. The batch export iterates through multiple types sequentially, each with an unbounded query.

Action: Add pagination limits or stream large exports. Consider a max row count with a warning for exports exceeding the threshold.

#23 — Missing Database Indexes
Medium
File
prisma/schema.prisma
Category
Performance

Critical query paths lack database indexes:

  • FcrReport(pondId, periodEnd) — queried with orderBy: { periodEnd: "desc" } in 3 places
  • Notification(pondId, read) — used for mark-all-read bulk update
  • ScheduleCommand(deviceId, appliedAt) — "find latest applied command" query pattern

Action: Add composite indexes to the Prisma schema and create a migration.

#24 — Cursor Pagination Bug in Audit Log
Medium
File
lib/actions/audit.ts:75-79,107
Category
Correctness

The audit log cursor uses createdAt without a secondary sort key. If two events share the same timestamp, events will be skipped or duplicated across pages. Other paginated endpoints (history.ts, growth.ts) correctly use id as cursor.

Action: Switch audit cursor to use id for consistency and correctness.

Only the (dashboard) route group has an error boundary. Errors in other route groups (login, landing page) fall through to the Next.js default error page, which may not match the application's design.

#29 — No Global Unhandled Rejection Handler
Low
Scope
Application process
Category
Reliability

No process.on('unhandledRejection') or process.on('uncaughtException') handlers. Several server actions (notifications.ts, audit.ts, biomass.ts) lack try/catch, meaning unhandled rejections from Prisma could silently crash the process.

Action: Add global handlers with structured logging. Also add try/catch to all server actions.

#30 — CSV Import Dynamic Typing Risk
Low
Files
lib/csv.ts:29-36
api/import/confirm/route.ts:52-171
Category
Input Validation

PapaParse is configured with dynamicTyping: true, which auto-converts types. The confirm route then uses Number(), Boolean(), and new Date() without checking for NaN, Infinity, or invalid dates. This could silently insert corrupted data into the database.

Action: Add Zod validation schemas for each import type (similar to the ingest route pattern).
