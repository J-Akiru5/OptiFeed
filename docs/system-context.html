1. How to use this document

This file is the single source of truth about the system for an AI that cannot browse the repository. It was produced by a full read-only audit of the code.

  • Section 2 is non-negotiable. Those rules exist because real damage has already happened (a production database wipe). Violating them is a failure.
  • The person giving you a plan will paste it alongside this document. The plan defines what to build; this document defines how the system works and what you must respect.
  • If your plan conflicts with a rule in Section 2, stop and ask the user rather than proceeding.
  • Section 19 is a third-party production-readiness assessment of this system (with independent verification) — if your plan touches feeding safety, data integrity, auth, CI, or monitoring, read it first.
  • Section 20 names the single authoritative execution plan (docs/OPTIFEED-INDUSTRY-GRADE-PLAN v3.md) and records the independent review that corrected it — if you were handed a different plan file, check §20 first.
  • When you do write code: match the existing conventions (Biome formatting — tabs, 100-col, double quotes; Conventional Commits; Server Actions in lib/actions/; no code comments unless asked), run pnpm lint, pnpm typecheck, pnpm build, and pnpm test before declaring work done.
  • Prefer editing existing files over creating new ones. Prefer small, single-purpose changes over rewrites.

2. Critical rules & landmines

Critical

Never run prisma migrate reset against production

It drops the entire database and recreates it from scratch. This already happened once and wiped all production data (ponds, devices, feeding history).

  • Production migrations: prisma migrate deploy
  • Local dev only: prisma migrate dev
  • prisma migrate reset: only on a local dev database you are willing to destroy.
Critical

Branch workflow

  • Work exclusively on the Karl branch (already exists, branched from develop).
  • Never push directly to develop or main. Every change reaches develop via a PR from Karl.
  • main is off-limits entirely — it is promoted from develop only by Jeff, only when a milestone is approved.
  • Sync before each task: git checkout Karl && git pull origin develop --rebase.
  • Keep PRs small and scoped to one task. Before opening a PR run pnpm lint, pnpm build, and the tests.
  • Commit messages must be Conventional Commits (feat:, fix:, chore:, refactor:) — commitlint enforces this on commit.
  • Never commit .env, .env.local, or any Supabase service-role key. Husky pre-commit hard-blocks staged .env* files.
  • Search for existing // TODO(karl): comments before building something from scratch.
Critical

"This is NOT the Next.js you know"

The app uses Next.js 16.2.10, which contains breaking changes. apps/web/AGENTS.md (injected into every tool call) instructs: read the relevant guide in node_modules/next/dist/docs/ before writing any code, and heed deprecation notices.

  • middleware.ts no longer exists — the file is proxy.ts (see apps/web/proxy.ts).
  • Local docs bundle lives at apps/web/node_modules/next/dist/docs/ (e.g. 15-route-handlers.md, 07-mutating-data.md, 18-upgrading.md, production-checklist.md).
  • apps/web/CLAUDE.md is just an import of AGENTS.md.
High

Security & correctness traps to not repeat

  • RLS policy mismatch: migration 20260831120000_add_rls_policies compares "ownerId" = current_setting('request.jwt.claims')->>'email', but Pond.ownerId stores a farmId slug (e.g. demo-farmer-1), not an email. If RLS is ever enforced, policies match nothing. Do not "fix" RLS casually — read the migration header first.
  • API auth is per-route, not middleware: proxy.ts matcher excludes /api/* entirely. Every new API route must do its own session check (@/lib/auth/session or @/lib/auth/with-auth) — a CI grep gate fails the build otherwise (allowlist: api/ingest, api/feed-command, api/schedule-sync, api/health).
  • Rate limiting is in-memory (a Map) — it does not work across serverless instances on Vercel. Do not assume it protects production endpoints.
  • /signup is publicly renderable. The admin check inside createUser (requireRole("ADMIN")) mitigates actual abuse, but proxy.ts has a dead/stub branch where a signup guard was intended.
  • Telemetry tables carry an immutable farmId stamp with no FK — never strip it, it must survive farm lifecycle deletes.
High

Stale docs that contradict the code (trust the code)

  • docs/vercel-deployment-checklist.md claims the app fails without Upstash Redis — false. Upstash was removed (commit 098771f); rate limiting is in-memory now. UPSTASH_* env vars are dead.
  • Firmware-Implementation (root) says the relay boots HIGH/closed — stale. Current firmware forces RELAY_OFF at boot (feeder must never dispense at boot). It also references EnergyReading, /api/relay-state, setRelayState() — none exist.
  • guidelines/Guidelines.md is an unfilled template; apps/web/README.md is the default create-next-app README. Neither is authoritative.
  • energy-monitoring-architecture-v2.html describes a different product line (EMU energy monitoring, PZEM-004T) that was merged/abandoned — most of it is not implemented here.

3. Product overview

OptiFeed is an aquaculture smart feeding management platform. A farmer manages ponds, logs biomass samples, and sets feeding parameters; an ESP32-controlled hopper feeder dispenses feed on schedule or on demand and reports telemetry back to a Next.js dashboard.

Main actors

  • Farmer / Operator / Viewer — logs into the web dashboard (farmId + PIN), manages ponds, views FCR/growth, triggers "Feed Now".
  • Admin — manages users, ponds, devices, hierarchy, audit trail.
  • ESP32 feeder — polls the API every 5 s, dispenses feed, posts telemetry.

Core loop

  • Farmer logs a biomass sample → feed grams auto-recalculated (with deviation guard).
  • Schedule edits queue a ScheduleCommand → ESP32 polls, ACKs → Pond updated.
  • "Feed Now" queues a FeedRequest → ESP32 polls within 5 s, dispenses, posts feed_dispensed.
  • Heartbeats update feed level / water temp / connectivity and raise notifications.
Note Terminology is inconsistent across the repo: root README.md says "Smart shrimp feeding management", the landing page meta says "Remote Feeding Control for Catfish Farms", and pantat_biomass_dataset.html refers to Pantat (a fish). Assume fish (catfish) in ponds unless a plan says otherwise — and if a task touches user-facing copy, ask which species is correct.

8. Auth & authorization

Login flow (farmId + PIN)

  1. Farmer enters farmId (e.g. demo-farmer-1) + 4–6 digit PIN.
  2. lib/actions/auth.ts → loginWithPin builds a synthetic email: `${farmId}@pond.optifeed.local` (buildPondEmail() in lib/auth/session.ts) and calls supabase.auth.signInWithPassword(email, password = pin).
  3. Prisma User is looked up by the email local-part (= farmId) to get the role.
  4. IP rate limit: 5 attempts / 60 s / IP. Lockout: 5 failed attempts → 15-minute lockout per farmId (UserLockout table, lib/auth/lockout.ts).

Roles & gating

  • ADMIN | OPERATOR | VIEWER.
  • requireRole(...roles) (lib/auth/session.ts) — redirects to /dashboard on failure. Used in app/[locale]/(admin)/layout.tsx and again inside every admin server action.
  • Route handlers use withAuth (lib/auth/with-auth.ts) — 401 without a Supabase session, passes { ownerId, user }.
  • Active pond selection = httpOnly cookie optifeed:pondId (1-year), set by switchPond(pondId) server action.
  • Client/server Supabase clients: lib/supabase/client.ts, lib/supabase/server.ts (both carry TODO(karl) notes).

10. ESP32 firmware

firmware/firmware-main/firmware-main.ino (713 lines) — target ESP32-WROOM-32U, the "unified OptiFeed controller" with a three-way fallback:

  1. SCHEDULED — DS3231 RTC-driven feeding; works with WiFi down.
  2. DASHBOARD — polled every 5 s from the backend.
  3. PHYSICAL BUTTON — GPIO 27; works when WiFi is down.
HardwarePinNotes
Relay (feeder motor, NO)GPIO 25RELAY_ON = HIGH when dispensing; forced OFF at boot
Push buttonGPIO 27INPUT_PULLUP, local manual dose (buttonFeedGrams)
DS3231 RTCGPIO 21/22 (I²C)Offline scheduling, default feed times 06:00 & 19:00
HC-SR04 ultrasonicTRIG 32 / ECHO 33Hopper feed level, ~5 m range, 30 ms pulseIn timeout
DS18B20 water tempGPIO 26Valid −10…80 °C; raw + per-device tempOffsetC

Protocol

  • HTTPS/JSON polling only — no MQTT, no WebSocket. Auth = X-Device-Token header; identity cross-checked against device_id (MAC).
  • Config: INGEST_URL, FEED_POLL_URL, SCHEDULE_SYNC_URL, DEVICE_TOKEN "esp32-tok-cict-001", DEVICE_MAC "A4:CF:12:7E:3B:09".
  • dispenseFeed(grams, source, requestId) — mutex first-acquire-wins; feedDurationMs = (grams / gramsPerSecond) * 1000.
  • Offline event queue: EVENT_QUEUE_SIZE = 50 — button feeds during outages are enqueued and flushed when back online.
  • Feed level: 3 ultrasonic reads → bubble-sort median → linear interpolation between hopperFullCm (=100 %) and hopperEmptyCm (=0 %).
  • pollScheduleCommand() distributes feeds_per_day evenly across schedule_start → schedule_end (interval = totalMinutes / (feedsPerDay − 1), midnight wrap), max 24 feed times.
  • OTA (setupOTA(), password = device token), NVS Preferences for WiFi creds + reboot count, exponential WiFi backoff (10 s → 60 s).

Docs: firmware/README.md (authoritative), Firmware-Implementation at repo root (partly stale — see §2), docs/esp32-nextjs-connection.html.

11. Domain logic & formulas

Core feed calculation — apps/web/lib/feed-calc.ts

DEFAULT_FISH_COUNT = 5000                                  // lib/constants.ts

totalBiomassG(population, avgWeightKg) = round2(avgWeightKg * 1000 * (population || 5000))
dailyFeedG(biomassG, feedingRatePct)   = round2(biomassG * feedingRatePct / 100)
feedPerMealG(biomassG, ratePct, feedsPerDay) = round2(dailyFeedG(...) / feedsPerDay)  // 0 if feedsPerDay <= 0

Locked reference values (asserted by lib/__tests__/feed-calc.test.ts — do not change without updating tests):

86 fish × 13.78 g  = 1185.08 g        (total biomass)
1185.08 g × 5 %    = 59.25 g/day
59.25 g ÷ 2        = 29.63 g/meal
1185 g × 3 % ÷ 3   = 11.85 g/meal

round2 adds an epsilon guard against floating-point half-value artifacts. All rounding is 2 decimals.

Derived helpers

  • lib/volumeCalc.ts → calculateNextFeeding(avgWeightKg, feedingRatePct, feedsPerDay, population) — the "next feeding amount" function used by Log Sample preview, PDF export, and device sync.
  • lib/feed-grams.ts → syncDeviceGramsForPond(pondId, config?) — recomputes and writes EnergyDevice.gramsPerFeeding from the latest BiomassLog.avgWeightKg + pond config; returns null if no sample exists.
  • lib/fcr-calculation.ts → calculateFeedRequirement(input), DEFAULT_FCR = 1.5: 
    totalBiomassGainKg = max(0, targetWeightKg - currentBiomassKg)
totalFeedNeededKg  = totalBiomassGainKg * fcr
dailyFeedRationKg  = totalFeedNeededKg / days
suggestedFeedingRatePct = (dailyFeedPerFishG / avgBodyWeightG) * 100
Guardrail

Biomass auto-adjust deviation guard — lib/actions/biomass.ts

avgWeightKg = sampleWeightKg / sampleCount. On save: ownership check → create BiomassLog + FishSample[] → compute calculateNextFeeding → DEVIATION_THRESHOLD = 0.5 (50 %): if |new − current| / current > 0.5 the auto-adjust is rejected and a biomass_logged DeviceStateEvent with autoAdjustRejected: true is recorded; otherwise gramsPerFeeding is updated. Sampling cadence = Pond.sampleIntervalDays (default 14).

Schedule change lifecycle

UI edit → ScheduleCommand(status: pending)
        → ESP32 GET /api/schedule-sync → status: sent  (+ DeviceStateEvent "command_sent")
        → device applies, POST /api/ingest schedule_acked → status: applied

  • Display value resolved by lib/schedule/resolve-current.ts → resolveCurrentSchedule(): pending/sent command → latest applied command → Pond row.
  • Stale-command expiry: STALE_SENT_MS = 10 min (actions/schedule.ts); stale feed-request expiry: STALE_DISPATCHED_MS = 10 min (actions/energy.ts); lazy FeedRequest expiry REQUEST_EXPIRY_MS = 60 s on every device poll.

12. Realtime & notifications

  • Supabase Realtime (postgres_changes INSERT on Notification, filter pondId=eq.<id>) in components/notification-provider.tsx.
  • Visual tiering (exact, by design): CRITICAL → sticky red banner + bell; WARNING/SUCCESS → 5-second toast + bell only; INFO → bell.
  • Categories: connectivity | feeding | pellet | pge | schedule | system. Reconnect auto-clears connectivity notifications.
  • ESP32 status in the dashboard comes from 5-second polling of /api/feed-command and /api/schedule-sync (not realtime).
  • Chat streams over SSE (data: {"text": ...}\n\n in api/chat/route.ts).
