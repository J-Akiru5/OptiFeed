API Regulation v1.1, adopted — and where it still leaks

One envelope, one instrumentation layer, one versioned tree, and two verification suites. The standard is now enforced in code and CI for OptiFeed — and the adoption surfaced six places where the standard itself can be gamed or is simply wrong.

TL;DR

The regulation was adopted as a project copy at the repository root, with the two decisions the standard requires a project to make: camelCase JSON for browser responses, and a 2027-06-30 sunset for the legacy unversioned tree. The canonical surface is now /api/v1/*, rewritten to the same handlers so the two trees cannot drift.

Instrumentation is a single withApi() wrapper plus a Prisma query extension. Every response — including 4xx, 5xx, timeouts, and unknown paths — carries Server-Timing and X-Request-Id; every request is classified WARN SLOW above 300 ms and ERROR VIOLATION above 400 ms. Query counting happens at the data layer, not in handlers, so it cannot silently measure zero.

The live §11 suites are implemented but not yet certified: this isolated worktree has no Supabase session cookie, and the only configured credentials resolve to the same database project ref as production, so running the suite there would violate the no-production-data rule. Deliberately refusing to measure is the correct behaviour, not a pass. What was verified end-to-end against a production build is the pipeline itself: rewrites, envelope normalisation, timeout handling, request-id echo, legacy sunset headers, and the 404 contract.

Verdict on the standard: keep the envelope, the status map, the 300/400 ms split, and the coverage floor. Fix the measurement source (use Server-Timing, not wall clock), add an auth budget, define ETag inputs, make indexing verifiable, and close the coverage-gaming holes. The detailed patch text is in docs/API_REGULATION_v1.2_PROPOSAL.md.

The request pipeline, as implemented

The regulation says instrumentation must live in the request pipeline, wrap the error layer, and be impossible to forget. In Next.js App Router there is no single router-level interceptor, so the wrapper is the pipeline: every exported handler is composed as withApi(withAuth(...)). A static CI check fails the build if a new route.ts exports an unwrapped handler.

1

Request id

Accept a client X-Request-Id only if it matches a safe pattern; otherwise generate a UUID. Carried through AsyncLocalStorage for the whole request.

2

Auth phase

withAuth verifies the Supabase session, resolves the farm from User.supabaseId, and records its own duration as auth;dur.

3

Handler + data layer

A Prisma $allOperations hook counts every query and accumulates db;dur, including raw SQL and transactions. No handler-level wrapping.

4

Envelope + error normalisation

Success uses { data, meta }; any 4xx/5xx response that is not already in the error envelope is rewritten to { error: { code, message, details, request_id } }. Passthrough routes keep their body.

5

Headers + logs

Server-Timing: total, db, app, auth, queries, X-Request-Id, optional Cache-Control/ETag, legacy Deprecation/Sunset. Slow and violation logs carry the route template, status, DB time, query count, and request id.

The timeout guard races the handler against an absolute budget and returns 504 TIMEOUT with the same instrumentation headers. The underlying promise is observed so a late failure never becomes an unhandled rejection — and it is not logged twice.

Where the standard itself leaks

Adopting the rules exposed places where a team can satisfy the letter of v1.1 and still ship a slow or incorrect API. These are the six amendments that change outcomes most; the full set of 22 with patch-ready wording is in the v1.2 proposal.

High

Wall clock is the wrong metric

§11.1 times the network and the server together. A fast API behind a slow proxy fails; a slow API on a warm keep-alive can pass. Gate on Server-Timing total and assert the client/server gap.

High

Auth is invisible

An identity-provider call per request is the most common unbounded dependency. v1.1 has no auth phase, so the cost hides in app. Add auth;dur with a ≤ 30 ms budget and require local JWT verification or a bounded cache.

High

ETags that can never match

Hashing the full envelope includes request_id, which changes every request. Our first implementation did exactly that and the 304 path was dead. Define ETag inputs and make 304 a required contract assertion.

High

Indexing is unfalsifiable

"Every filter/sort column is indexed" cannot be checked in review. Require a query registry plus EXPLAIN (ANALYZE, BUFFERS) artifacts, and fail on a sequential scan above a declared row threshold.

High

Coverage can be gamed

The 90 % floor is measured against a list the same PR can edit. Freeze the hot manifest, require a reason for changes, add traffic-weighted coverage, and expire skips after three runs.

Medium

The budget numbers disagree

A 1 000 ms statement timeout sits under a 150 ms DB slice and a 2 000 ms absolute timeout under a 400 ms max. Align them: 250 ms DB, 1 000 ms absolute. A timeout larger than the budget is a hang detector, not a budget.

Also proposed: idempotency semantics (scope, TTL, replay, 409), compound cursors, retryable/retry_after_ms in errors, TTFB vs stream duration, a 64 KB compressed cap, cookie-auth CSRF/cache rules, observed deprecation counters, client LCP/INP budgets, OpenAPI diffing, and query-count growth tests at limit=1 vs limit=100.

Burn-down backlog

The regulation is a contract, not a one-time refactor. These are the items adoption found, ordered by user-visible impact. Each one names the rule and the evidence.

P0

Make auth cheap — fast path shipped

getClaims() now verifies locally for asymmetric keys, with a 30 s session cache and a 60 s farm cache. A cache hit makes no Supabase call and no DB lookup. Staging still needs to publish the auth p95.

P0

Dedupe the session lookup per render — shipped

getCurrentUser() is wrapped in React cache(), so a render tree or server action performs one lookup instead of one per call. Route handlers use the session/farm caches.

P0

Fold the prediction schedule query into the first wave

/api/predict-feeding awaits three reads, then a separate schedule lookup. Join it into the same Promise.all and re-measure.

P1

Move imports/exports to jobs

15–35 s guards and 50 k-row synchronous CSV/ZIP/PDF work violate the 400 ms max. Return 202 with a status URL and process in the background.

P1

Enforce statement_timeout and instrument RSC

Set the Postgres role timeout (and align it with the 150 ms DB slice). Add the same ALS timing to dashboard server components so slow first renders are visible.

P2

Drop the extra limiter write and the header fetch

The Postgres rate limiter writes on every API call; the header fetches /api/user-role after hydration. Move the limiter to a shared cache and read the role in the layout.

P3

Add load tests and a schema source of truth

k6 at 2× peak for L3 endpoints, and an OpenAPI document that the contract suite derives from so field changes cannot slip through.

The benchmarking subagent

A dedicated read-only subagent was added at ~/.config/opencode/agents/nextjs-supabase-benchmark.md, with a reusable harness at ~/.config/opencode/bin/nextjs-supabase-audit.mjs. It is scoped to Next.js + Supabase apps and produces ranked, measured optimisation opportunities — not a generic Lighthouse dump.

What it measures

HTTP p50/p95/p99 from Server-Timing and wall clock, query count growth, payload size, auth phase, cold-start vs warm, bundle output from next build, and Web Vitals where a base URL is available.

What it audits statically

Unbounded findMany, missing select, sequential awaits and RSC waterfalls, getUser() per request, RLS predicates that re-evaluate auth.uid() per row, pooler mode/region mismatch, and routes missing instrumentation.

Safety

Read-only: no edits, no installs, no pushes, no deployments. It refuses to run destructive database commands and reports resource deferrals instead of inventing numbers.

Output

A ranked table (impact × confidence × effort), the evidence for each finding, and a reproducible command. The parent agent verifies the evidence before acting on it.

Honest limitations

  • No live latency certification. The suite exists and fails correctly without a credential, but the L2 baseline still needs a seeded environment and a session cookie.
  • Statement timeout is policy-only. Prisma cannot apply SET LOCAL per request without a transaction; the role-level setting must be applied in a migration.
  • SSE measures TTFB. /api/chat reports time to first byte, not stream completion; the v1.2 proposal separates the two metrics.
  • No RSC instrumentation. `withApi` covers route handlers; dashboard server components still lack Server-Timing, so a slow first render is invisible in this layer.
  • No load test. §11.4 is not implemented; L3 certification is incomplete until it is.
