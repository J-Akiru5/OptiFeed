01

Summary

PakaonAI is a multi-tenant feeding platform for brackish-water shrimp farms: an ESP32 controller at the pond, a Next.js dashboard in the farmer's hand, an offline-capable progressive web app, and an AI assistant that reads the pond context the user is allowed to see.

TL;DR

The system is broad, the engineering evidence is real, and the evaluation is not finished.

Fifteen functional domains are implemented at fdfc830, across three console surfaces and one device firmware. The repository carries re-checkable engineering evidence for most ISO/IEC 25010 characteristics — but the performance workflow is currently failing to execute, there is no requirement-to-test traceability matrix, and no respondent questionnaire data exists yet.

The film therefore sells the product and the engineering discipline, and explicitly labels the evaluation as work in progress. It does not show an ISO score, a certification, or a final FCR result.

Five things this document establishes

  1. The feature surface is much larger than the landing page suggests. Beyond feeding, there is tenant administration, platform administration, device provisioning, calibration, audit, background jobs, exports and imports, and a full calendar.
  2. Multi-tenancy is real but not complete. Organization → Farm → Pond → Device is implemented with role scoping and audit; the planned FeederUnit/Controller split and tenant purge are not.
  3. The engineering evidence is specific and re-checkable. 3,335 unit tests, 92.42% line coverage on apps/web/lib, 35 passing E2E tests, 54 cross-browser smoke passes, and an executed restore drill.
  4. There are named gaps, and they are written down. No MFA, no provider-backup verification, no physical-device testing, an unbuilt Docker image, and a performance gate that creates no jobs.
  5. One five-minute film can serve three audiences if the evidence layer is sequenced after the product story rather than mixed into it.

System in one page

PakaonAI is one product made of four planes that have to agree with each other: the experience plane in the browser, the application plane on Vercel, the data plane in Supabase, and the edge plane at the pond.

Experience

A farmer samples the pond, the platform turns that sample into a ration and a schedule, the controller dispenses it and reports back, and the record survives to harvest — with or without connectivity.

02

Architecture

The system is a conventional server-rendered web application with an unusual edge constraint: the pond must keep feeding when the cloud is unreachable. That constraint explains most of the architecture — the device's local clock, the bounded event queue, the offline snapshots, and the deliberate refusal to queue feed commands in the browser.

Request path

  1. A page request hits a locale segment (/en, /hil, /tl) and resolves the session on the server.
  2. Authenticated layouts resolve the active pond and the caller's organization scope before rendering any tenant data.
  3. Mutations go through server actions that re-check role, pond ownership, and rate limits — the UI is never the authority.
  4. Device traffic uses a separate path: token hash lookup, constant-time comparison, approval-state check, then ingest or command polling.
  5. Every API response carries a request id and Server-Timing; the v1 envelope wraps data and errors consistently.

03

Tenancy model

The tenant boundary is the Organization. What sits below it — farms, ponds, cycles, devices, samples, feed events, audit rows — is reached through an organization scope that is resolved on the server at query time.

Architecture detail

The hierarchy is derived, not a stored foreign-key chain

There is no Farm.orgId and no Pond.orgId. Organization scope is resolved by following active memberships to users, then each user's unique farmId, then ponds owned by that farm login. This works and is enforced server-side, but it means the tenancy model is a query-time chain rather than a database-enforced hierarchy, and the organization and membership tables have no foreign keys.

What is implemented

  • Organization with a type — individual, cooperative, company, LGU, or academic — and a status lifecycle.
  • Membership with one of four roles, plus independently grantable permissions.
  • Farm reached through the member's farm login. One account maps to one farm.
  • Pond under a farm, with an active crop cycle, fallow state, notification preferences, and devices.
  • Device — the ESP32 controller — attached to a pond, with calibration, telemetry, and command history.

What that means in practice

Do not overclaim

“An organization owns many farms” is only true through many member logins

Because Farm.ownerId and User.farmId are both unique, a cooperative with three farms needs three separate member accounts. There is no in-product organization switcher and no second farm on a single login. The schema does not yet express “one organization, many farms, one owner”.

The planned Feeder Unit → Controller split is also unbuilt: one EnergyDevice row is both the logical unit and the physical controller, so replacing a controller today breaks the device history chain. The schema permits several devices per pond, but the application reads the first one.

Where isolation is actually enforced

Application code is the enforcement boundary: server-side scope resolution, ownership filters, and guarded server actions. Row-level security policies exist and protect the Supabase Data API, but Prisma connects as the database owner, which bypasses RLS. RLS is therefore defence in depth, not the primary control.

Three gates, not one

Membership role is not the only write authority

Three checks run independently. The tenant console requires an owner or admin membership. A write also requires the legacy User.role to be admin or operator, and the specific action may add a named permission. That legacy role still decides several write paths — biomass, time, settings, and farm actions — so a membership viewer whose legacy role is admin can pass the write gate where no permission check is attached. Two permission names (view_dashboard, view_reports) are defined but not enforced; data visibility comes from farm ownership.

This is a real finding, not a documentation detail: it is one of the open authorization issues in the tracker, and it should be described accurately in the defense.

Platform authority is deliberately heavier

  • Dangerous platform actions require a reason, write an audit row, and require a step-up re-authentication within a five-minute window.
  • View-as is read-only, time-boxed, banner-visible, and audited. It is not an impersonation free-for-all.
  • Tenant suspension blocks member writes without deleting data, and is reversible.
  • MFA is not implemented. The step-up is a fresh password check, not TOTP. A mfaEnrolledAt column exists but is never written.

Feeding control path

This is the core loop of the product. Every other feature either feeds it or reads from it.

Three trigger tiers, one dispense gate

  1. Scheduled. The controller's real-time clock fires at the configured times with no network required.
  2. Dashboard. The controller polls for a remote command every five seconds and dispenses on request.
  3. Physical. A falling-edge interrupt on the feed button captures a short press even while the main loop is busy with HTTPS.

All three routes call the same dispenseFeed() function, so the safety limits cannot be bypassed by choosing a different trigger.

Offline model

Offline support is not “the app works offline”. It is a specific contract about what is cached, what is queued, and what is refused.

The contract

ActionOffline behaviour
View dashboard, schedule, growth, harvest, historyLast cached snapshot, with an offline banner and the last-synced time
Submit a biomass sampleQueued in an append-only outbox with a client event id; replayed idempotently on reconnect
Feed nowRefused. Feeding offline belongs to the controller's RTC schedule or the physical button
Edit schedule or crop cycleRefused
Harvest or calibrateRefused
Controller feedingContinues on the local clock; events queue on the device and sync later

The deliberate refusals are the interesting engineering decision. A queued “feed now” that replays six hours later is worse than an error message, because it can double-feed a pond. The system chooses a visible failure over a silent, delayed hazard.

09

Device provisioning

Provisioning is two separate acts: joining the controller to a network, and granting it an identity in a tenant.

What actually happens, in order

  1. Register the unit first. A platform administrator registers the MAC to an organization and pond (reason and step-up), or a tenant owner or admin adds it under the organization's registration policy. The token is shown once.
  2. Power the controller with no stored network. It makes no API calls and runs only the setup portal, while still feeding on its RTC schedule.
  3. Join PakaonAI-XXXX from a phone. The branded page scans 2.4 GHz networks, tests the credentials before saving, and asks for the Device ID and token.
  4. Save and restart. A successful join writes Wi-Fi and identity to non-volatile storage; a failed join writes nothing and returns the reason. The unit then appears online in the tenant device list.
  5. Label the unit and print the sticker sheet.
Security caveat

The setup access point is open

The setup AP has no password or proof-of-possession. Anyone within range of a unit that is in setup mode can reach the portal and overwrite its Wi-Fi and identity. Per-unit proof-of-possession is in the plan but not implemented. On a farm this is a bounded risk; in a shared or public space it is a real one, and it should be named in the defense rather than discovered by the panel.

Important distinction

The sticker QR joins the setup hotspot — it does not claim a unit

The printed QR encodes a Wi-Fi join payload for the setup access point. It contains no credentials and no claim token. Tenant registration is by MAC address with an approval policy. A true self-claim flow — scan a code, bind a factory unit to an organization and pond — is planned, not built.

components/admin/device-sticker.tsx · lib/provisioning-ap.ts

Identity and reset

  • The device authenticates with a token whose SHA-256 hash is used for lookup and compared in constant time; the approval state is checked on every request. A plaintext token column is still retained as an interim measure, which is a documented security debt.
  • The token is shown once at registration. A later reveal is audited and rate-limited; rotation invalidates the old token immediately.
  • Holding the Wi-Fi reset button for five seconds clears network credentials. Holding the factory reset for ten seconds clears identity as well. Both have a boot grace period and release-to-arm behaviour so a stuck button cannot wipe a unit at power-on.

01

What this evaluation is

This is an engineering self-assessment against the eight product-quality characteristics of ISO/IEC 25010:2011. It is not a certification, not an audit, and not a respondent score.

Boundary

A repository cannot be ISO certified

ISO/IEC 25010 defines a product quality model. It does not certify an organization or a codebase. ISO 9001 and ISO 27001 certify management systems, and neither is claimed here. What follows is evidence that the product was engineered with the model in mind, with named gaps.

Version note

2011 versus 2023

This dossier uses the 2011 eight-characteristic model: functional suitability, performance efficiency, compatibility, usability, reliability, security, maintainability, and portability. The 2023 revision restates usability as interaction capability, portability as flexibility, and adds safety — nine characteristics. The repository cites both versions in different documents. Pick one for the paper and stay consistent; the film uses the eight-characteristic framing because that is what the evidence was assembled against.

Backup and recovery

The recovery story has a verified half and an unverified half, and they should be presented separately.

Verified

06

Device operations

Fleet operations are split between the tenant, who owns the pond relationship, and the platform, which owns the registry and firmware.

Routine operations

  • Registration — by MAC, with organization policy deciding auto-approval or admin approval.
  • Approval — pending devices are visible in the tenant console and do not receive commands until approved.
  • Token lifecycle — shown once, revealed only under audit and rate limit, rotated with immediate invalidation.
  • Calibration — feed rate, hopper distance, temperature offset, device time, daily cap, and a recalibration interval with drift reminders.
  • Firmware — signed manifests, A/B slots, pending-verify rollback, and a MAC canary channel. There is no rollout UI; the channel file is uploaded manually.
  • Labels — print sheets with unit data and a setup-hotspot QR.

Failure handling

A device that stops heartbeating is flagged by the device-watch cron. A device that loses Wi-Fi keeps feeding on its RTC schedule. A device that browns out holds safe mode rather than closing the relay. The failure modes are designed to fail toward “no feed” rather than “unlimited feed”.

App capture plan

Screen capture is the highest-risk part of the production, because a single real name or token in frame is a privacy incident. Capture against a dedicated demo tenant, never against production.

Setup

  • Create a demo organization, two farms, three ponds, three devices, and thirty days of plausible feeding history.
  • Use fictional names: “Demo Farm”, “Pond A”, “Pond B”. No real farmer, member, or email address.

Sound and music

The audio should disappear. If a viewer notices the music, it is too loud or too interesting.

Voiceover

  • Record in a treated room or a closet with soft furnishings; a dynamic microphone at 15–20 cm, slightly off-axis.
  • Target −18 dBFS average, peaks below −6 dBFS. Record room tone for 20 seconds.
  • De-noise lightly, compress gently, and de-ess. Do not use a “movie trailer” voice preset.
  • Record to the locked picture, not to the script's estimated timings. Re-time the SRT from the recorded audio.

Music

A free Suno instrumental is acceptable if the licence for the account tier permits the intended publication. Generate after the edit timing is locked, not before.

Suno prompt

Instrumental bed, 78 BPM

“Cinematic ambient technology, warm marimba and soft piano, gentle pulse, optimistic documentary, 78 BPM, no vocals, no lyrics, loopable, five minutes, restrained, space for narration.”

Generate two or three options, choose the one with the least melodic movement under the voice, and keep the generation record with the licence note. Have a licensed fallback ready from a library with a clear commercial licence.

Captions and SRT

The SRT is a deliverable, not an afterthought. It must match the burned-in captions exactly, and both must match the recorded voiceover.

Rules

  • Two lines preferred, three maximum for a sentence that cannot be split cleanly. 20 characters per second reading speed.
  • Minimum cue duration 1.2 seconds; maximum 7 seconds. Gap between cues 2 frames.
  • No speaker labels. No sound descriptions unless a sound is meaningful to the story.
  • Keep numbers as digits on screen even when the voice says the words, except where a digit would be ambiguous.
  • Re-time after the final voiceover. Never ship an SRT generated from the script's estimated timings.

Decisions at the freeze

These are the questions the film cannot answer for itself. They are ordered by how much they change the cut.

  1. Does PR #357 merge? If yes, the film can show Pakoy executing an approved action. If no, it shows a proposal and an approval, and says the write surface is in review.
  2. Does PR #359 merge? If yes, the performance gate can be described as enforced. If no, the evidence beat says the gate is being repaired.
  3. Which ISO model does the paper use? The 2011 eight-characteristic model or the 2023 nine-characteristic model. The film must match the paper, and the on-screen footnote must name the year.
  4. Is there approved growth or FCR data? If yes, one number may appear, with its method and date. If no, the film says results are under review.
  5. Is the physical feeder available? If yes, shoot the five hardware shots. If no, replace them with 3D and app footage and drop the pond dawn shot rather than fake it.
  6. Human or synthetic voice? A human voice is warmer; a synthetic voice is faster to revise. Either is acceptable if the SRT matches.
  7. Which environment is filmed? Preview or production, with seeded demo data. Never capture against a tenant that contains real farm records.
  8. Is the legal review complete? If not, the film avoids compliance-adjacent claims and says the policies are published drafts.
  9. Which music track? Choose after picture lock, record the licence, and keep the fallback.
Default if unanswered

Choose the conservative branch

If a decision is not made by the freeze, the film uses the smaller claim: proposals instead of writes, “gate under repair” instead of “gated”, “results pending” instead of a number, and 3D instead of a pond shot. A smaller true film is better than a larger one that collapses under a question.

Glossary

Terms used across the dossier and the film. Where a term has a product-specific meaning, that meaning is given first.

ABW
Average body weight. The mean weight of the sampled shrimp, used to estimate pond biomass.
Biomass
Estimated total weight of shrimp in a pond: average body weight multiplied by the estimated population.
Crop cycle
One stocking-to-harvest period for a pond. A pond has at most one active cycle at a time.
Fallow
The state after harvest, before the next stocking. Feeding and schedule changes are blocked.
FCR
Feed conversion ratio: feed consumed divided by biomass gained. Lower is better. Harvest FCR is computed; the historical report series is imported.
SGR
Specific growth rate, a daily percentage measure of weight gain.
Ration
The feed allocated to a pond for a period, derived from biomass and a feeding rate.
Dose
A single dispense, expressed in grams and converted to auger run time by calibration.
Tenant
An organization. The isolation boundary for data, members, and configuration.
Organization scope
The server-resolved set of organizations, farms, and ponds a request may touch.
RBAC
Role-based access control: owner, admin, operator, viewer, plus individual permissions.
RLS
Row-level security in Postgres. Present as defence in depth for the Data API; the application uses a database owner connection, so RLS is not the app's primary boundary.
Step-up
A fresh password check required before a dangerous action. Not multi-factor authentication.
View-as
A read-only, time-boxed, audited session in which a platform administrator sees a tenant console.
Platform admin
A separate authority record that grants cross-tenant access. It is not a tenant role.
PWA
Progressive web app. Installable, with a service worker and an offline shell.
Outbox
An append-only local queue of biomass samples waiting to sync.
Idempotent replay
Re-sending a queued event without creating a duplicate, using a client-generated event id.
Snapshot
A cached read model of a page, used when the network is unavailable.
RTC
Real-time clock on the controller. It keeps the feeding schedule when Wi-Fi is down.
NVS
Non-volatile storage on the ESP32, holding Wi-Fi credentials and the device token.
OTA
Over-the-air firmware update. Signed, A/B slotted, with pending-verify rollback.
GLB
The binary glTF 3D model format used by the viewer and the film renders.
ISO/IEC 25010
A product quality model. The 2011 revision defines eight characteristics; the 2023 revision defines nine. Not a certifiable management system.
axe-core
An automated accessibility rule engine. The project runs the whole default rule set on six surfaces.
SBOM
Software bill of materials. Generated as CycloneDX in CI.
RPO / RTO
Recovery point objective and recovery time objective. Documented at 24 hours each.
ISUFST
Iloilo State University of Fisheries Science and Technology. The institution the capstone is built at.
