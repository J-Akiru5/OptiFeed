ESP32 Communication Flow (Every 5 Seconds)

1. Heartbeat Telemetry POST /api/ingest

Device sends: WiFi signal, feed level %, water temperature, feeder status, RTC status. Server updates EnergyDevice.lastSeenAt and creates FeedLevelLog entries (throttled to every 30min or >5% delta).

2. Feed Command Poll GET /api/feed-command?device_id=X

Device checks for pending "Feed Now" requests from the dashboard. Server returns: pending feed request (grams) OR idle. Response also pushes: grams_per_feeding, button_feed_grams, calibration config.

3. Schedule Sync Poll GET /api/schedule-sync?device_id=X

Device checks for pending schedule changes. Server returns: new schedule command (start/end times, feeds/day, feeding rate) OR "no change". Response also pushes: calibration config (hopper_empty_cm, hopper_full_cm, grams_per_second).

4. Feed Dispensed Event POST /api/ingest

After a scheduled or manual feed completes, device sends: event_type: "feed_dispensed", grams dispensed, source (scheduled/dashboard/button). Server creates FeedEvent + FeedRequest records.

5. Schedule Acknowledgment POST /api/ingest

After device applies a new schedule, sends: event_type: "schedule_acked", command_id. Server marks ScheduleCommand as "applied" and updates Pond schedule fields.

6. Offline Queue Flush POST /api/ingest (batch)

If WiFi was down, device queues events in a 10-slot array. On reconnect, flushes all queued events sequentially. Current limitation: only 10 events stored; older events are lost if queue overflows.

Security Hardening
TaskEffortDetails
Protect /api/user-role with auth Small Currently exposes user roles to anonymous users via unauthenticated GET. Add withAuth wrapper or session check. This is the most exposed endpoint right now.
Add ownership verification to schedule.ts Small updateScheduleCommand() and toggleDevicePause() get the caller's ownerId but never verify that the pondId/deviceId actually belongs to that owner. A malicious user could pass another user's pondId.
Add ownership verification to history.ts Small getFeedEvents() accepts a deviceIds array directly from the caller with no ownership check. Should verify all device IDs belong to the caller's pond.
Add ownership verification to growth.ts Small getFeedLevelLogs() accepts a deviceId from the caller with no ownership check. Should verify device belongs to the caller's pond.
Restrict CORS on device API routes Medium Currently Access-Control-Allow-Origin: * on /api/ingest, /api/feed-command, /api/schedule-sync. Since ESP32 doesn't enforce CORS, this only exposes the endpoints to browser-based abuse. Change to specific origins or remove entirely.
Add Row-Level Security (RLS) to Supabase Medium The deployment checklist documents a proposed SQL migration. Apply it so the Supabase anon key (exposed client-side) can't bypass application-level authorization. Without RLS, any user can read/write any data if they know the anon key.
Rotate secrets and clean up .env Small Real Supabase credentials and Gemini API key exist on disk. Rotate all keys and ensure they're only in Vercel environment variables.
Remove 'unsafe-eval' from CSP Small Current Content-Security-Policy includes script-src 'self' 'unsafe-inline' 'unsafe-eval'. Audit whether Gemini or chat actually needs eval, and remove if not.

Key Design Decisions to Make

These decisions affect multiple phases. Make them early to avoid rework.

Multi-pond: Cookie vs URL Param vs Context?

How should the selected pond be persisted across page navigations?

Recommendation: Use a cookie (optifeed:pondId) that the middleware reads and injects into server components via searchParams. Cookies persist across tabs and survive page refreshes. URL params cause ugly URLs. React context doesn't work across server components.

Multi-feeder: Independent or Coordinated?

If a pond has 2 feeders, do they both execute the same schedule independently, or split the feeding?

Recommendation: Start with independent (each feeder runs the full schedule). It's simpler, and in practice most farms have 1 feeder per pond. Add coordinated mode later as an advanced feature if needed.

Device Provisioning: Simple vs Full Captive Portal?

How do farmers connect new ESP32 devices to WiFi and register them?

Recommendation: For MVP, use the admin-flash flow (register on dashboard, flash token to ESP32 via USB). A full captive portal is more user-friendly but adds significant firmware complexity (AP mode, web server, WiFi config page). Add it in Phase 3.

OTA Updates: When to Add?

Over-the-air firmware updates are critical for field devices but add security surface.

Recommendation: Add OTA in Phase 3 (after multi-pond is stable). Use HTTPS-based OTA (not ArduinoOTA which uses multicast DNS). Sign firmware images with a private key to prevent tampering.
