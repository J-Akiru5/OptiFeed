Superadmin & Multi-Tenancy for PakaonAI

This plan turns PakaonAI from a one-farmer-per-login system into a multi-tenant platform. Organizations own farms, members have roles, and a Syntaxure superadmin governs everything with audited "god mode" controls. The structure is copied on purpose from the Syntaxure EMS architecture (v3). That system already solved the same problems for energy monitoring units and recorded, in writing, the mistakes worth not repeating.

Verdict

The model is sound, and the foundations are further along than they look

PakaonAI already has two of the hardest EMS pieces: hashed device-token lookup and trigger-based telemetry ownership stamps. The work that remains is mostly additive: an organization layer above Farm, a feeder-unit/controller split below Pond, and a superadmin console whose every action is reasoned, re-authenticated where it matters, and audited in the same database transaction.

The one thing that must not be underestimated is tenant isolation. Today it lives entirely in application code, because Prisma connects as the database owner and bypasses RLS. Phase M2 exists to make that safe.

What EMS taught us

The EMS v3 document is valuable less for what it built than for what it caught late. Three of its lessons shape this plan directly, and one EMS pattern needed physical adaptation because PakaonAI's board is wired differently.

Lesson 1

Never let one column mean two things

EMS added owner_type to mean "who owns the hardware" and then built it to mean "which hierarchy level the assignment targets." Its provider-ownership decisions ended up with no schema to stand on. PakaonAI gets ownershipParty (PROVIDER | CUSTOMER) as its own column, and M1.2's acceptance test is literally a review that no field carries two meanings.

Lesson 2

Stamp ownership before multi-tenant data exists

EMS's one blocking conflict was telemetry that couldn't prove which customer it belonged to. PakaonAI already stamps the farm via trigger; M1.3 extends the same trigger to stamp org, feeder unit and installation before the second tenant writes a single row.

Lesson 3

Verify claims, don't trust reports

EMS recorded a build hash inconsistent with its own file size and a "dead code" finding that was wrong (Next.js 16 renamed middleware.ts to proxy.ts). Every phase report here must separate code-, build-, deployment- and physically-verified, and the three long-lived branches are compared from a full clone before any conclusion.

Domain model

Who owns what, and for how long

Five ideas must stay separate for this system to be correct: who the tenant is, who owns the hardware, where the hardware is installed right now, what a person is permitted to do, and what the feeder will physically allow. The domain model gives each of these its own entity or column, so none of them can silently stand in for another.

The hierarchy T1 · T2

The tenant is an Organization. An individual farmer is simply an organization of type INDIVIDUAL with one owner, so there is no separate code path for "small" customers; a cooperative or an LGU uses the same model with more members and farms. People never own farms directly. They hold a Membership in an organization, and the membership carries a role plus a materialized set of revocable permissions (the EMS pattern, already proven there).

Below the pond, the design separates the Feeder Unit, a permanent logical identity with a serial number, a QR code and a lifetime history, from the Controller, the ESP32 board that can burn out and be swapped. A FeederInstallation row records each period a unit spends with a specific org, pond and controller, which is what makes "who saw this data, and when" answerable after reassignment.

"Feeder Unit" is a placeholder name (open question O1). Because it becomes a table name in Phase M1, the name has to be settled first; renaming a table after real tenant data exists is exactly the kind of one-way door this plan tries to avoid.

Ownership is not tenancy T6

Because units can be sold (customer-owned) or leased (provider-owned), the question "who may move this unit to another customer" has different answers for different units. A leased unit belongs to Syntaxure, so the superadmin may take it back and reassign it, but the previous tenant must never see the next tenant's data. A sold unit belongs to the farmer, so Syntaxure cannot move it, though it can help transfer it when the farmer asks.

Design rule

ownershipParty is a dedicated column on Feeder Unit with exactly one meaning. Lifecycle position lives in status; current tenancy lives in orgId; physical placement lives in pondId; history lives in installations. Four facts, four places.

Feeder lifecycle

A unit moves through seven states. Two details matter. First, CLAIMED without a pond is a real, visible state, not an error: a farmer may claim a unit before deciding where it goes, and the dashboard should show it as "unplaced" (EMS decision #5). Second, cross-org reassignment always closes the current installation and opens a new one, so each tenant's history is sealed.

Ownership stamps on telemetry Already half built

Every telemetry row (feed events, feed requests, state events, feed-level logs, biomass logs, fish samples, FCR reports, notifications, schedule commands) already receives a farmId stamp from a database trigger at insert time. The stamp has no foreign key on purpose: it is immutable history that must survive farm deletion and transfer. This plan extends the same trigger, renamed stamp_telemetry_ownership(), to also write orgId, feederUnitId and installationId.

Stamping in a trigger rather than in application code was the right call when it was made, and it remains right: every writer is covered, including seeds, imports and code nobody has written yet. A row written after a unit changes hands carries the new tenant's stamp, and the old tenant's queries, which filter by their own orgId, simply never see it.

Tenancy & superadmin

Two doors: one for tenants, one for god mode

Tenant users pass four gates before they can touch anything. The superadmin passes through a completely separate door that demands a reason, sometimes a fresh re-authentication, and writes an audit row in the same transaction as the action itself. If the audit write fails, the action fails.

Authorization resolution

The four tenant gates are unchanged from EMS, where they were verified live repeatedly: authenticated (resolved by Supabase user id, never by the email's local part), member of the resource's organization, resource within that membership's scope, and the specific permission not revoked. A suspended organization fails the membership gate for everything except its data-export page.

Non-members get 404, not 403, so the existence of another tenant's pond is not confirmed to someone probing ids. Members missing a permission get 403, because they already know the resource exists.

Roles and permissions

Permissions are materialized into rows when a membership is created, which means an owner can revoke a single permission from a single person, for example removing control_feeder from an operator who keeps overfeeding, without inventing a new role.

Isolation: the critical finding S3 · verified

Critical

Row-level security does not protect the app today

The app's Prisma connection uses the postgres owner role, and the migration that enabled RLS on User says so explicitly: the owner bypasses it. The existing RLS policies protect only Supabase's REST and Realtime surfaces. For every page and API route, the only thing keeping one farmer out of another's data is a correct where clause written by hand.

With one farmer per login that risk was contained. With organizations, memberships, org switching and a superadmin console, the number of queries that must filter correctly multiplies, and one missed filter is a cross-tenant leak. The plan answers with two layers, sequenced by urgency.

ADR-PK-01 · Layer 1 · Phase M2

A tenant-scoped database client is the only way tenant code touches tenant data

Decision
forOrg(orgId), a Prisma client extension, injects the org filter on every read and rejects writes carrying a different orgId. A self-check rule fails the build if tenant code imports the raw client for a tenant model.
Proof
One negative test per tenant model and per API route: org A cannot read or write org B.
Trade-off
Still app-layer: a bug in the extension itself is a single point of failure, which is why Layer 2 exists.
ADR-PK-02 · Layer 2 · Phase M8 (commercial gate)

Tenant traffic runs as a non-owner database role under RLS

Decision
A dedicated app_tenant role; RLS policies compare each row's orgId to current_setting('app.org_id'), set per transaction by forOrg(). Superadmin and cron keep the owner role.
Why later
It touches connection pooling and every policy; worth doing carefully once, before money flows, not rushed before a defense.
Do not
Use FORCE ROW LEVEL SECURITY on the owner role; it breaks the app (hardening-plan note).

The superadmin boundary T5 · T10 · T13

God mode moves out of the UserRole enum into its own PlatformAdmin table, so "tenant admin" and "platform admin" can never be confused. The controls below are split between what the capstone defense needs and what must exist before the first paying tenant. That is the same sequencing EMS chose, with the reason requirement added from day one.

Step-up is required for: suspending, purging or restoring a tenant; read-write impersonation; any remote feeder command; revoking a controller; cross-org reassignment; changing a commission rate; adjusting the ledger; and granting or revoking platform admin.

Accepted risk

T10 gives demo users the full superadmin capability set for a limited window. That is Jeff's explicit call, as in EMS. The plan narrows the exposure without overriding it: a demo grant still cannot purge, fire a feeder or impersonate in write mode without the same reason and step-up a permanent admin needs, and every action under a temporary grant is visibly distinct in the audit explorer.

Devices & safety

From factory flash to the farmer's pond

Units leave Syntaxure already carrying their identity. Farmers never see or type a device token: they scan a QR code to claim the unit and enter only their WiFi on the feeder's own setup page. Two physical buttons handle the field problems of a new router and a full reset. Nothing a superadmin does can make a feeder dispense beyond its safety caps.

Factory flash

Today the firmware compiles the token in as #define DEVICE_TOKEN "esp32-tok-cict-001" and bakes the MAC into the polling URLs, so every unit needs its own build. Under this plan, Syntaxure creates the Feeder Unit and Controller rows, flashes the device id and a freshly generated token into the ESP32's NVS storage, and stores only the token's SHA-256 hash. The plaintext is displayed once, at flash time, and never persisted. That also closes S5's leftover: the plaintext token column is dropped. Since units can be reflashed, existing demo units migrate the same way.

Self-claim and WiFi setup T7

The claim code printed on the unit is random with 128 bits of entropy, stored hashed, single-use, rate-limited by the existing PostgreSQL limiter, and expires 90 days after assignment (proposed). Scanning it in the app binds the unit to the farmer's organization and, optionally, a pond. Only then does the farmer power the unit. With no WiFi stored, it raises its own access point, PAKAON-XXXX, and the setup page asks for the network name and password only, because identity is already on the device.

Dual reset buttons Adapted from EMS

EMS solved "the farm changed its router" with a dedicated WiFi-reset button and kept full factory reset separate. PakaonAI adopts the same pair but cannot reuse EMS's pins: GPIO 32 and 33 already drive the HC-SR04 hopper sensor. The proposal uses GPIO 18 and 19, which are not boot-strapping pins, not input-only, not reserved for flash, unused by current firmware, and support the internal pull-up. Confirm them on the physical board before soldering.

Controller replacement

EMS left one conflict open: the schema could express a revoked controller, but nobody verified that the replacement flow revoked the old one atomically. PakaonAI closes it by design. Replacing a controller is a single transaction: the old board is marked revoked, the new one active, and the installation closed and reopened with the same org and pond. A test proves the old token gets 401 on its very next request. Calibration (grams per second, hopper distances, temperature offset) moves from the controller to the feeder unit, so a board swap doesn't send the farmer back to recalibrate.

Safety precedence Non-negotiable

God mode is powerful over data, not over physics. Every feed command, from a farmer's phone, the superadmin console, an AI assistant or a schedule, passes server caps first and firmware caps last. The firmware is the highest authority because it is the only layer that still works when the network, the server or a person's judgement fails.

ADR-PK-05

Superadmin never bypasses feed caps

Decision
No override path in the API or firmware. A remote feed to an empty hopper produces feed_refused, and that is the correct outcome.
Future
Any "reset a refusal remotely" feature needs human acknowledgement and can never override an active local safety condition (EMS #8).

Commercial model

Farmers pay when they sell

PakaonAI takes a percentage of gross sales on each harvest dispatch, and maintenance is billed per service on top. For farmers this removes the up-front cost that stops most smallholders from adopting technology. For Syntaxure it means carrying hardware cost and risk for months before the first peso arrives. The model works if three things are built in: proof of what was sold, a minimum per cycle, and lease targeting by pond size.

Opinion

The revenue share is the right headline for the market and a strong pitch: "we earn when you earn." It is not safe as the only revenue line. The charts below show why: on small ponds, a leased ₱20,000 unit can take more than two years to pay for itself, before counting cloud, connectivity and support.

Dispatch to statement T11 · T12

The weak point of any revenue share is that the platform doesn't witness the sale. PakaonAI is unusually well placed to narrow that gap, because it already estimates pond biomass from fish samples and population. Each dispatch is checked against that estimate. When the reported weight differs from the estimate by more than a threshold (25% proposed, open question O4), the dispatch goes to a superadmin verification queue and earns no commission until it is resolved.

The ledger is append-only: corrections are new rows with a reason, never edits. Commission rates live in dated agreements, so a rate change never rewrites past statements. Payments are recorded manually at first. A payment gateway integration (PayMongo or Xendit) is deliberately out of scope until there are enough tenants to justify it.

Hardware payback Illustrative

Inputs: ₱20,000 per unit (Jeff's BOM estimate), ₱150/kg farmgate price, and a 4.5-month grow-out cycle. The price and cycle are planning values from a 2026 hito guide (₱130–180/kg range). Because revenue only arrives at harvest, payback is counted in whole cycles. Harvest per cycle per unit is the unknown that dominates everything, so it is the x-axis.

Reading the chart: at about 1,000 kg per cycle and 5%, a leased unit repays its hardware at the third harvest, roughly 13.5 months. At 500 kg it takes 27 months at 5% and over 3 years at 3%. Ponds that small are better served by a customer-owned unit, a higher rate or a per-cycle minimum, not a lease.

The cash gap

The second chart follows one leased unit's cumulative cash at 1,000 kg per cycle. Every line starts ₱20,000 underwater and stays flat through the first grow-out (shaded) because nothing has been sold yet. This is the company-side weight Jeff anticipated. It scales linearly with deployed units, so 50 leased units means about ₱1M deployed before the first harvest, plus operating costs not shown here.

Data lifecycle

Suspend, export, purge, without starving fish

Tenants can be suspended, can export their data, and can be deleted. Deletion follows T9: access is revoked at once, a grace period allows export or cancellation, then personal data is hard-deleted. Anonymized telemetry from Syntaxure-owned units is retained. Throughout, a billing or account state never stops a feeder from feeding.

Tenant states T9

Animal welfare

Suspension never stops feeding

A suspended tenant cannot change anything, but its feeders keep running the last schedule stored in firmware. The server stops accepting new schedule pushes; it never sends a "stop." Fish dying over an unpaid statement would be both a moral failure and the fastest way to lose every farmer's trust.

Export

Any owner can export their organization's ponds, telemetry, biomass history, dispatches and ledger as CSV in a ZIP, including while suspended or pending deletion. The export runs through the same tenant-scoped client as everything else, and has its own negative test proving it contains nothing from another org.
